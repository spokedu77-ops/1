# 화·금 담당 강사가 다른 수업의 수업안 연결 오류

## 확인된 원인

`삼성 11남 탁구+생체`는 화요일 조승제, 금요일 김세현 담당 수업이다.
10월 29일 생성된 10월 30일 연기 기록의 `POSTPONE_SNAPSHOT`에 해당 세션이
11월 6일 김세현에서 11월 10일 조승제로 변경된 전후 값이 남아 있다.
연기 함수는 세션 ID를 유지하면서 목적지 요일의 날짜와 담당 강사로 변경했다.
수업안은 세션 ID만 참조하므로 10월 15일 작성된 10월 16일 김세현 수업안도
그대로 남았다. 10월 16일부터 11월 6일까지의 이동 경위는 확인되지 않았다.

최근 추가된 날짜 검증은 이 과거 불일치를 저장 시 거부했다. 화면의 고정
`00.00` 템플릿과 이전 안을 날짜 변경 없이 복사하는 동작도 날짜 검증과 충돌했다.

## 이번 수정

- 날짜(KST) 또는 담당 강사가 변경되면 수업안 전체 행과 기존 세션 정보를
  비공개 이력에 보존한 뒤 활성 수업안에서 분리한다. 원문 날짜·강사명은 덮어쓰지 않는다.
- 같은 세션이 원래 날짜·시간·강사로 돌아오면 본문 날짜까지 일치하는 가장 최근
  미복구 이력만 복구한다. 이동 중 새 강사가 작성한 안도 먼저 보존한다.
- 이력에는 FK cascade를 두지 않아 세션 정리로 원본까지 삭제되지 않게 한다.
- 비공개 이력은 브라우저에 노출하지 않는다. 서버가 확인한 사용자 ID로 호출하는
  service-role 전용 RPC만 본인의 같은 수업 그룹 이력을 조회할 수 있다.
- 저장·수정·삭제는 담당 확인, 세션 잠금, 수업안 ID 검사와 쓰기를 하나의 RPC에서
  처리한다. 이전 ID로 0행 갱신하고 성공 응답하는 동작을 제거했다.
- 화면은 실제 날짜·시간으로 빈 양식을 생성한다. 명시적 복사 시 날짜·시간만
  변경하며 회차·본문은 작성자가 검토한다. 초기 조회가 끝나기 전에는 저장하지 않는다.
- 정산·회차·보조 강사·피드백·완료 상태·일정 충돌 검증은 유지한다.

같은 강사라도 수업일이 바뀌면 원본을 자동으로 고쳐 쓰지 않고 보존한다.
작성자는 이전 수업안에서 명시적으로 복사해 재사용할 수 있다.

## 적용 및 검증

- DB migration `20261110022144_lesson_plan_schedule_ownership` 적용.
- `sql/repairs/20261110_teacher_lesson_plan_assignment.sql` 적용: 원본 ID·수정 시각·
  본문 날짜·연기 스냅샷을 검사한 뒤 해당 한 건만 보존 및 분리.
  결과: 11월 10일 조승제 수업 활성 수업안 0건, 김세현 원본 보존 1건.
- `supabase/tests/lesson_plan_schedule_ownership.sql` 통과: 실제 화·금 연기 RPC,
  새 담당 작성, 과거 담당/수업안 ID 거부, 날짜 검증, 이력 접근 제한, 연기 복구,
  같은 강사의 날짜 이동, 수업료·시간 변경, RPC 권한. 합성 데이터는 전부 롤백.
- 실제 문제 수업에서 `service_role`로 새 RPC 작성·수정·삭제 및 현재 배포 API와
  동일한 INSERT/UPDATE 경로가 성공함을 확인. 검증 쓰기는 롤백해 빈 상태 유지.
- 날짜/복사/오류 안내와 API 인증·권한 회귀 테스트 19개 통과. 변경 파일 ESLint 통과.
- 변경 파일과 의존성에 대한 TypeScript 검사 통과. 전체 TypeScript 검사는 기존
  `.next` 및 `.next-local-integration` 생성 validator가 존재하지 않는 두 storage cleanup
  라우트를 참조하는 오류 4건으로 실패했으며, 해당 생성 파일은 수정하지 않았다.
- 후속 수정: 두 라우트는 `e0ba279ae`에서 삭제됐으나 생성 타입에 참조가 남아 있었다.
  `tsconfig.json`에서 별도 검증용 `.next-phase6`, `.next-local-integration` 생성물을
  기본 검사 대상과 분리했다. 기존 `npm run typecheck`의 `next typegen`으로 현재
  라우트 타입을 재생성한 뒤 전체 TypeScript 검사도 종료 코드 0으로 통과했다.
  현재 `.next/types/validator.ts`와 앱 소스 1,964개가 검사에 포함되고, 별도 검증용
  캐시 파일이 0개 포함됨을 확인했다. `ignoreBuildErrors` 등 오류 무시 설정은 변경하지 않았다.
- 신규 보존 테이블은 의도적으로 RLS 정책 없이 클라이언트 접근을 차단한다.
  보안 점검의 `rls_enabled_no_policy` INFO는 이 설정에 따른 것이다.

DB 보호 로직과 이번 데이터 복구는 적용됐으며, 화면·API 소스 변경은 별도 앱 배포가
필요하다. 커밋·푸시·앱 배포는 수행하지 않았다. 브라우저에서의 실제 로그인·저장
동선에 대한 렌더링 검증은 수행하지 않았다.
