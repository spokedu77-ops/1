제품 피드백 잡의 상태 전이는 Supabase와 앱 API에 설계돼 있다. 이번 조사는 운영 DB를 읽지 않았다.

## 위험 패턴

- 도구는 실패했는데 모델이 성공처럼 말할 수 있다. 성공 로그가 없어 사용자가 대조할 수 없다. 시스템 지침이 “호출하지 않았으면 정책 거절로 단정하지 말라”고만 말한다.
- 중복 실행: 피드백 잡은 멱등 complete를 과거 E2E에서 봤다고 보고서가 말한다. 비서 MCP에는 idempotency key가 없다.
- 승인 없는 외부 변경: 지침과 Gmail 도구는 로컬 승인 파일을 요구한다. Calendar는 `user_approved` 플래그를 모델이 넘긴다. 모델이 true로 호출하면 서버가 사람 클릭을 따로 봤는지까지는 이번엔 호출 인자 검증 코드를 전수하지 못했다. 발송 테이블이 0인 것은 발송 성공 기록이 없다는 뜻이지, 가드가 완벽하다는 뜻은 아니다.
- 사용자가 로그를 제품 화면에서 볼 경로: 피드백 잡은 교사 화면 쿼리가 있다. MCP 실패 로그는 탐색기 파일뿐이다.

오늘 데이터 변경 검증(성공 호출인데 무변경, 실패의 성공 표시)은 **재현하지 않았다.** 쓸 수 있는 관찰은 “성공 경로가 기록되지 않는다”는 구조적 사실이다.
